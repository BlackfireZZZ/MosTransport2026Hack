# AGENTS.md

## Миссия репозитория

Мы создаём систему поддержки диспетчерских решений для прогнозирования пассажиропотока московского наземного транспорта. Приоритеты: корректность прогноза и данных, объяснимость, надёжность, скорость разработки, визуальный polish.

Эти правила действуют для всего репозитория. Локальный `AGENTS.md` может уточнять их, но не ослаблять критерии доказательства.

## Карта agentic-контрактов

- Шаблон постановки задачи: `docs/agentic/TASK_SPEC.md`.
- Матрица проверок: `docs/agentic/VERIFICATION_MATRIX.md`.
- Границы полномочий: `docs/agentic/PERMISSIONS.md`.
- Передача работы между агентами: `docs/agentic/HANDOFF.md`.
- Длительные планы: `docs/exec-plans/README.md`.
- Правила контура находятся в ближайшем `backend/AGENTS.md`, `frontend/AGENTS.md` или `ml/AGENTS.md`.

## Главное правило: сначала доказательство, потом изменение

Агент не может применять изменение, пока не сформулирует, почему оно будет работать корректно.

До редактирования агент обязан:

1. Выписать проверяемое утверждение: какое наблюдаемое поведение изменится, а какое останется прежним.
2. Найти существующий контракт, тест, тип, миграцию или официальный источник, подтверждающий способ реализации.
3. Определить минимальную проверку, способную опровергнуть решение: unit/integration-тест, сборку, миграцию на чистой БД, SQL-план или smoke-тест.
4. Проверить границы влияния по карте архитектуры и найти потребителей изменяемого контракта через `rg`.

Доказательство — воспроизводимая цепочка: предпосылки → реализация → проверка → наблюдаемый результат. Если проверку невозможно выполнить, изменение не применяется; агент фиксирует блокер и просит решение человека.

## Поиск сложных решений

Для нового комплексного решения — технологии, алгоритма, схемы данных, безопасности, масштабирования или нетривиального UX — сначала ищем схожие примеры в интернете.

- Приоритет: официальная документация, стандарты, статьи авторов технологии, engineering posts с измерениями.
- Для ML: первичная статья, документация библиотеки и воспроизводимые benchmarks.
- Не переносить код вслепую. Зафиксировать контекст примера, сходства, различия и риски для наших объёмов и SLA.
- Аргумент записать в отчёте агента. Для решения, которое трудно отменить, создать ADR в `docs/decisions/`.
- Если интернета нет, не выдавать память модели за исследование: обозначить ограничение и опираться на локальные контракты.

## Обязательный рабочий цикл

1. Прочитать `README.md`, `DESIGN.md`, эту инструкцию и ближайшую архитектурную документацию.
2. Проверить `git status`; не перезаписывать чужие незавершённые изменения.
3. Сформулировать гипотезу и критерии приёмки.
4. Исследовать аналоги, если решение новое или комплексное.
5. Начать с теста/контракта либо объяснить, почему существующая проверка достаточна.
6. Внести минимальное связное изменение в правильный слой.
7. Запустить узкие проверки, затем `make check`; для инфраструктуры — `docker compose config` и smoke-тест.
8. Проверить diff на секреты, generated-файлы, нарушение границ и изменение публичных контрактов.
9. В отчёте перечислить доказательства, допущения и непроверенные риски. Не писать «должно работать» без результата команды.

## Изоляция крупных задач через git worktree

Задача считается крупной, если выполняется хотя бы один критерий:

1. Планируется изменить восемь или более файлов, кроме generated-файлов.
2. Изменение затрагивает три или более контуров из `backend`, `frontend`, `ml`, `compose/infra`, `.github`.
3. Меняется публичный API, схема БД/Alembic, auth/permissions, production dependency, runtime/deploy/CI или контракт данных/признаков/модели.
4. План содержит три или более независимо проверяемых implementation milestone либо рассчитан более чем на 90 минут/одну сессию.
5. Два или более агентов будут параллельно редактировать файлы.

Для крупной задачи главный агент автоматически создаёт отдельный git worktree **до первого изменения файла**. В основном checkout разрешены только чтение, поиск и оценка diff; писать в него запрещено. Исключение: агент уже находится в dedicated worktree, то есть текущий путь отличается от первого `worktree` в `git worktree list --porcelain`; вложенный worktree тогда не создаётся.

Безопасный lifecycle:

1. Зафиксировать основной путь, `HEAD`, текущую ветку и `git status`; чужие изменения не stash/reset/переносятся автоматически.
2. Создать уникальную ветку `agent/<task-slug>-<timestamp>` и соседний worktree от явно записанного base SHA. Если требуемое состояние существует только в незакоммиченных изменениях, остановиться и запросить решение человека.
3. Каждый пишущий агент работает только в назначенном worktree и своей области владения. Общие runtime-ресурсы должны иметь уникальные project name/порты/volumes.
4. Перед cleanup показать `git status`, ветку, HEAD и местонахождение результата. Worktree удаляется через `git worktree remove <path>` только после интеграции/явного отказа и только при чистом status; `--force`, ручной `rm -rf`, удаление непушенной ветки и очистка чужих worktree запрещены.
5. В итоговом отчёте привести base SHA, путь и ветку worktree, подтверждение проверок, способ интеграции и факт cleanup либо причину, почему worktree сохранён.

## Параллельная работа агентов

Независимые исследования, ревью, тестовые прогоны и анализ рисков следует параллелить через субагентов. Один файл или один контракт в конкретный момент имеет одного владельца; параллельные агенты не редактируют пересекающиеся области. Главный агент собирает результаты, разрешает противоречия и лично запускает итоговый quality gate.

Обязательный формат передачи результата определён в `docs/agentic/HANDOFF.md`. Параллельная запись допустима только в непересекающихся worktree/областях; финальную интеграцию и проверку нельзя делегировать.

## Архитектурные границы

- `domain` не импортирует FastAPI, SQLAlchemy, Pydantic или framework-код.
- `application` оркестрирует сценарии через протоколы; HTTP и SQL здесь не живут.
- `infrastructure` реализует хранилища, внешние клиенты и ML adapters.
- `api` валидирует транспортный контракт и вызывает application service; бизнес-логика в handlers запрещена.
- Frontend feature не обращается к `fetch` напрямую: только через `src/api` и feature hooks.
- `components/ui` — shadcn primitives без продуктовой логики.
- Обучение и batch inference отделены от online web worker.

Нарушение границы допускается только с ADR, планом обратной миграции и контрактным тестом.

## Данные и ML

- Сырые валидации и телематика неизменяемы; исправления — новой версией преобразования.
- Каждая выборка имеет диапазон дат, версию признаков, timezone `Europe/Moscow` и защиту от leakage.
- Split временных рядов только по времени; случайный split запрещён.
- Baseline обязателен. Новая модель принимается при улучшении согласованных метрик на нескольких временных срезах.
- Прогноз сохраняет `model_version`, `generated_at`, горизонт и интервалы неопределённости.
- Изменение признаков сопровождается тестом схемы и граничных дат/часовых поясов.

## База данных и API

- Схема меняется только Alembic-миграцией. Проверять upgrade на чистой БД и план отката разрушительных миграций.
- API backward-compatible по умолчанию. Удаление поля требует новой версии или deprecation.
- Большие таблицы не читаются без диапазона времени и ключа агрегации.
- На тяжёлых запросах проверять индексы и `EXPLAIN (ANALYZE, BUFFERS)` на репрезентативном объёме.
- В логах нельзя хранить персональные идентификаторы пассажиров или секреты.

## Frontend и дизайн

- `DESIGN.md` — источник истины для токенов, плотности, типографики, состояний и визуализации.
- Экран диспетчера — рабочая поверхность: фильтры и результат видны без marketing hero.
- Интерактивное состояние имеет loading, empty, error и keyboard-accessible вариант.
- Цвет не является единственным носителем смысла. Числа используют tabular numerals.
- UI primitive добавляется через shadcn CLI или по официальному исходнику и остаётся локальным.

## Критерии готовности

Изменение готово, когда критерии приёмки выполнены; тесты и static checks прошли; миграции и контракты синхронизированы; документация обновлена; нет скрытого fallback, маскирующего ошибку; отчёт содержит команды и фактический результат.
