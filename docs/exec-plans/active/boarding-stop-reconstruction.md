# План: восстановление остановок посадки по временным логам валидаций

Дата: 26.09.2026. TASK-062 — подготовка плана. TASK-063 — выполнение по явному запросу пользователя; см. журнал исполнения в конце.
Владелец плана: ML lead. Требования: поддержка RQ-03; восстановление скрытых
посещений — исследовательское расширение, не уже доказанная возможность данных.

## 1. Результат и проверяемая гипотеза

Восстановить для успешной валидации остановку посадки, направление и предполагаемое
посещение остановки конкретным вагоном. Использовать секунды оплаты, совместную
активность валидаторов, порядок остановок и допустимое время движения. Сохранять
альтернативы и неразрешённые события; не гарантировать привязку каждой строки.

H1: на независимо размеченных рейсах последовательное сопоставление всплесков
даёт более высокое покрытие при той же точности, чем простое сопоставление по
расписанию/интервалам времени. H2: явная модель пропусков/длительности уменьшает
сдвиги на одну остановку и ложные развороты относительно жадного baseline.
H3: увеличение сложности оправдано только воспроизводимым выигрышем на отложенных
рейсах/датах, а не более красивой картой или меньшей собственной loss.

Опровержение: при независимой проверке алгоритм систематически сдвигает остановки,
не различает направления, либо не превосходит baseline при одинаковом покрытии.
Без независимой разметки H1/H2 остаются непроверенными; можно доказать инварианты
и устойчивость, но нельзя объявить высокое качество восстановления.

Нельзя обещать AGI: это специализированный алгоритм обратного восстановления с
неполными наблюдениями. Цель — максимум достоверной информации, а не максимум
непустых stop_id. Первое решение должно работать без нового GPU/LLM-сервиса.

## 3. Граница ML и защита остального приложения

План не меняет runtime/API/DB/frontend, текущий CatBoost, labels или submission.
Будущая реализация — новый изолированный offline-пакет `ml/src/tramflow_ml/boarding/`
и отдельная CLI-команда; это предполагаемый путь, сейчас такого пакета нет.

Проверенные границы:

- `identity/align.py` требует available_at, `identity/types.py::Matched` описывает
  exact_id/name_route_direction/geo_nearest. Наши вероятностные оценки туда не
  подставлять и отсутствие available_at не «исправлять» event_at.
- `ingestion/` имеет собственную дедупликацию и контракты; использовать только
  совместимые утилиты после проверки, не пропускать raw организатора через адаптер,
  который молча меняет количество successful rows.
- `route_models/` и старый `tramflow-ml` CLI остаются без изменений. Новые результаты
  не попадают в forecast.v1 или serving автоматически.
- Новые экспериментальные файлы имеют собственную schema_version и inference_method;
  отдельная будущая публикация требует нового ADR/контрактных тестов/проверки UI.
- Raw ZIP immutable; временные индексы/результаты в ignored ML artifacts. Сохранить
  archive/member hashes, code SHA, конфигурацию, seed, версии зависимостей и источников.
- Карточные/водительские/бортовые идентификаторы не выводить в отчёт. Для артефактов
  сравнения использовать локальные непрозрачные ключи; соответствие хранить отдельно.

Будущая реализация является большой R2-задачей: выделить новый worktree от проверенного
HEAD через make agent-create до редактирования кода. Не продолжать её автоматически
как часть этого документа. Вопросы gold-данных и источников не разрешаются установкой библиотек.

## 4. Что именно является скрытой переменной

Для каждого vehicle-session рассматриваем несколько гипотез:
`route_pattern, direction, trip_boundary, stop_visit_sequence, arrival/departure,
payment_delay, device_clock_offset`.

Всплеск оплат и остановочное посещение — разные объекты. Одна остановка может дать
несколько всплесков; несколько близких остановок могут слиться в одну плотную группу.
Оплата после отправления относится к предыдущей посадке, а не обязательно к текущему
положению вагона. Нет оплат — не доказательство отсутствия остановки или пассажиров.

При отсутствии якорей одна последовательность временных интервалов может одинаково
соответствовать нескольким участкам/направлениям. Система должна сохранять такую
симметрию, а не выбирать stop1 или направление 0 по умолчанию. Допустимый результат:
«восстановлена относительная последовательность, абсолютные stop_id не определены».

Якоря по силе: независимое фактическое посещение/GPS → проверенное назначение рейса
с временем → историческое расписание (план, не факт) → повторяемый профиль движения
→ геометрический prior. Автоматически найденная длинная пауза не становится независимым
якорем конечной. В каждом результате хранить происхождение якоря и его погрешность.

## 5. Этап A — аудит пригодности логов, до выбора алгоритма

### A1. Один полный потоковый проход

Читать оба raw CSV; ограничивать исследования событиями до 2025-11-01. Для январь–октябрь
сохранить все rejected rows только в служебной диагностике: target-масса равна только
успехам. Хвосты объединять по event time; прочтение ровно одного файла исказит сентябрь.
Проверить header/encoding, ошибочные строки, timestamp resolution и допустимый route.

Минимальные извлекаемые поля: member+row_ordinal, tran_no, tran_date_time, validation_result,
ngpt_route, garage_number, bus_exit_no, device_no. Карточный hash не нужен первой версии;
если потребуется исследование повторов, делать отдельный локальный проход с обоснованием.

Стабильный event_key = source-member identity + row ordinal. Совпадение tran_no не
означает автоматический дубль. Две копии могут считаться двумя строками target источника.
Ledger обязан сохранить, какие строки исключены из matching по качеству, но учтены
в исходной successful mass. Исследовательская dedup-гипотеза — отдельная версия.

### A2. Метрики идентичности

По route/day и по часу: доля пустых/sentinel IDs, количество устройств/вагонов,
доля событий с полным ключом; отдельно успехи и отказы. Идентификаторы сохранять строками.
Построить interval-based отношения device→garage и garage→route/exit, измерить
одновременные конфликты, миграцию устройства, переиспользование номера между днями.

Не объединять два устройства только потому, что их всплески похожи. Не разделять
вагон по каждому переключению route без проверки. При конфликте vehicle-связи —
карантин/несколько гипотез, а не выбор большинства с потерей minority rows.

### A3. Временное качество

Измерить ties на секунде, сортировку, отрицательные gaps, пики строго на границе
минуты, периодические пачки, независимую синхронность устройств одного вагона.
Несколько одновременных устройств могут означать посадку или общий timestamp batching.
Поэтому отдельно сравнить внутривагонную и межвагонную синхронность.

Смещение часов устройства, задержка оплаты и начало рейса частично неразличимы без
якоря. Автокорреляция не доказывает clock correction. Рассматривать offset как
диагностическую гипотезу; при отсутствии независимого подтверждения не менять event time.
Исправленное время — отдельная колонка с версией; официальный target сохраняет исходный час.

### A4. Пилот

Выбрать 2 маршрута с разными плотностями из 1/7/11/12, минимум несколько полных дней
будни/выходные и пик/непик. Выбор фиксировать по coverage-аудиту до оценки алгоритмов;
плохие vehicle-days не удалять из знаменателя отчёта. Route5 — обязательный отрицательный
контроль: нельзя восстановить поток из одной неуспешной строки.

Выход A: inventory.json,identity_quality.json,time_quality.json,cohort_manifest,
таблица отсутствующих данных, decision go/no-go. Если стабильного vehicle-key нет,
не смешивать оплаты разных вагонов в маршрутные всплески; ограничить задачу
подтверждёнными устройствами/сессиями либо остановить абсолютный matching.

## 6. Этап B — исторический каталог и версии маршрутов

Представлять маршрут набором направленных patterns, а pattern — упорядоченными
visits: `(pattern_version,direction,sequence,stop_id)`. Повторный stop_id в петле
допустим. Разные платформы/направления не объединяются по названию.

Для каждой версии: valid_from/to, known_at если известно, источник, координаты,
длины перегонов по путям, флаг доказанного соответствия 2025. Не использовать
справочник 2026 как известный в 2025. Если историческая версия неизвестна, статус
`pattern_version_unverified`; результаты только сценарные/relative, не certified stop labels.

Не создавать маршрутную последовательность по кратчайшему пути OSM без доказательства
реального pattern: общая сеть допускает несуществующие пассажирские рейсы. Частичные,
укороченные и кольцевые рейсы — самостоятельные варианты; отсутствие варианта
должно давать pattern_mismatch, а не насильственную привязку к полной линии.

Ожидаемое число остановочных посещений определяется выбранным рейсом и границами
наблюдения. Нельзя использовать 622 строки workbook,489 остановок или один N на весь
номер маршрута. Запись, начавшаяся в середине рейса, не должна «дополняться» до конечных
как будто наблюдалась полностью.

## 7. Этап C — сессии и границы рейсов

Сначала отсортировать события по проверенному vehicle-key и event time с устойчивым
разрешением ties через event_key. Разбивать только при подтверждённых несовместимостях;
длинный gap создаёт кандидата boundary, не гарантированный разворот.

Сохранять конкурирующие варианты: продолжение рейса с тихими остановками,
отстой/конечная, смена направления, смена маршрута, неполнота данных, clock anomaly.
Дата гражданских суток и service day — разные поля; не обрывать рейс в 00:00.
Не копировать чужое правило «всё до 06:00 — предыдущий день» без локального основания.

Первое наблюдение не обязано быть началом рейса. Сессия без якоря получает
open_left/open_right и распределение возможных стартовых offsets по pattern.
Направление выводится совместно с остановками и boundary, а не один раз жадно.
Сравнить независимое декодирование рейса и декодирование последовательности рейсов
одного вагона: второе может связать конечные, но не должно распространять одну ошибку
на весь день. На сменах резко увеличивать неопределённость и сохранять альтернативы.

## 8. Этап D — обнаружение всплесков, несколько методов

| Метод | Что проверяем | Слабое место | Роль |
|---|---|---|---|
| D0: gap clustering | Новый burst после большого inter-event gap | Цепочка небольших gaps склеивает несколько остановок | Простой baseline, обязательно max-span |
| D1: адаптивный gap | Threshold зависит от vehicle-session density, обучается только на train | При плотном потоке может ошибочно нормализовать всё как один burst | Дешёвый кандидат |
| D2: 1D DBSCAN | Плотные интервалы и шум по секундам, несколько устройств | Два близких stop visits сливаются; редкие оплаты становятся noise | Сравнение со span-constrained clusters |
| D3: смена интенсивности | Бины времени, Poisson/overdispersed count cost, changepoints | Пустая область не равна перегону, batching выглядит как посадка | Альтернатива локальным порогам |
| D4: совместная скрытая модель | Посадочные группы выводятся вместе с движением и задержкой | Больше неидентифицируемых параметров и вычислений | Только после устойчивого D0+DP |

Предлагаемая стартовая сетка гипотез (не установленные физические константы):
gap10/30/60 секунд; max_span30/90/180 секунд; bins1/5/10 секунд; отдельные singleton
события никогда не удалять. Отсечь явно бессмысленные сочетания на synthetic tests,
далее ограничить бюджет сравнений; не перебирать весь Cartesian product на holdout.

Burst хранит event_keys, start/end, count_success,count_rejected,device_count,
межсобытийные квантили, max_gap, span, concentration, batching_flags. Начало/конец
оплат — не arrival/departure. Event-to-burst mapping обратим; альтернативная
сегментация может разделить или объединить burst без потери событий.

Не назначать все оплаты внутри burst одной остановке навсегда. На следующем этапе
разрешить split/merge и event-level payment delay. Отказы можно сравнить как
auxiliary timing signal отдельной абляцией; они не увеличивают число посадок.

## 9. Этап E — baseline и рекомендуемый основной алгоритм

### E0. Три обязательных baseline

B0: без идентификации, всё unresolved — показывает честную исходную coverage.
B1: ближайшее время исторического расписания при доступном validated trip binding;
если расписания нет, baseline explicitly not applicable, не подменять его придуманным.
B2: burst-gap + жадное монотонное сопоставление по ожидаемым временам перегонов;
неизвестный старт перечисляется, первое событие не закрепляется за stop1.

### E1. Основной первый кандидат: монотонное DP/beam alignment

Состояние: pattern/direction, индекс ожидаемого visit, индекс event/burst, интервал
начала рейса, режим движения/отстоя, ограниченный clock/payment-delay scenario.
Переходы: match, несколько bursts→один visit, разделение burst между visits,
переход через visits без наблюдаемых оплат, ложный burst/outlier, boundary,
смена pattern при допустимой конечной, open start/end. У каждого перехода явная причина.

Стоимость гипотезы складывается из:
- согласованности временного промежутка с распределением суммарных travel/dwell times;
- правдоподобия распределения payment delays;
- ограничений порядка/направления/якорей;
- штрафов неподдержанных пропусков/split/merge и смен рейса;
- правдоподобия наблюдаемых устройств при данном vehicle assignment.

Время перехода через 3 перегона нельзя сравнивать со временем одного. В travel-time
prior использовать длины реальных путей, отдельные dwell terms, неопределённость
пробок/светофоров; фиксированная скорость для всех маршрутов — только слабый baseline.
Нельзя обучать priors только на dense bursts и объявлять их точными для ночи.

Молчание останавливает рост уверенности. Пропуски не должны быть бесплатными, но
штраф за каждый «тихий» stop не должен заставлять модель придумывать burst. Posterior
silent-stop зависит и от ожидаемой интенсивности посадок, и от полноты источника;
эти величины без gold не считать известными. Сравнить несколько priors sensitivity.

Выдавать top-K путей и неразрешённую массу. Если beam pruning убрал вероятные
альтернативы, фиксировать approximation flag; top-K score gap не равен вероятности
правильности. При исчерпании бюджета возвращать undecoded, не случайный лучший путь.

### E2. HMM / HSMM

HMM — baseline последовательной вероятностной модели; скрытое состояние включает
visit/travel/direction, наблюдения — интенсивность оплат и устройства. HSMM явно
моделирует длительность стоянки/перегона и предпочтительнее, если геометрическая
длительность обычного HMM плохо согласуется с размеченными рейсами.

Длительности измеряются в секундах или фиксированных временных бинах. HMM по
индексам транзакций без учёта inter-event time моделировал бы количество оплат,
а не длительность движения: такой вариант для времени не допускается.
По возможности вычислять marginals/forward-backward, а не только Viterbi path.
Clock offset, payment delay и начало рейса сильно связаны: без якорей фиксировать
часть параметров как сценарии и показывать чувствительность. Полностью свободное
EM может объяснить любые данные неверными остановками; это не доказательство качества.

### E3. Когда усложнять

Particle/beam smoothing для меняющейся скорости, factor graph совместных constraints
и EM для travel-time priors — последующие кандидаты. Допуск только при выигрыше
над E1 на независимой разметке и приемлемом времени. RL/Transformer/GNN не стартовый
путь: без истинных stop labels они оптимизируют нашу эвристику. LLM не назначает
остановки отдельным оплатам; текст новостей не решает идентифицируемость траектории.

## 10. Контроль «не потеряли ли остановки»

### 10.1 Считать ожидаемые позиции, не число всплесков

Для выбранной гипотезы полного pattern с N посещениями вести ledger каждой позиции:
`observed_payment_support`, `latent_visit_no_payment_support`,
`unresolved_visit`, `independently_confirmed_not_served`.
Последний статус требует внешнего подтверждения; отсутствие burst его не создаёт.
Latent visit — гипотеза алгоритма, не зафиксированная остановка вагона.

Каждая ожидаемая позиция получает ровно одну категорию; сумма категорий=N —
только структурная проверка ledger. Если pattern/границы неизвестны, N неизвестно;
считать candidate-specific ledgers, не искусственную общую полноту.

Пример: pattern содержит 20visits, обнаружено 12bursts. Допустимы 20 посещений с восемью
нулевыми наблюдениями, частичный рейс, другой pattern, потеря источника или ошибочная
сегментация. Нельзя объявить «потеряли 8 станций» и распределить оплаты по ним поровну.
И наоборот 24bursts при 20visits могут означать раздробленную посадку, длинный рейс,
смену вагона или несколько рейсов; нельзя механически сжать до 20.

### 10.2 Временной бюджет

Для каждой гипотезы считать распределение суммарного travel+dwell+terminal time,
остатки между наблюдениями, количество подряд неподдержанных visits, допустимость
начала/конца. Большой residual либо необычное число пропусков увеличивает uncertainty
и порождает альтернативу; не «чинится» равномерным растягиванием времени.

Локальная проверка: между двумя надёжными якорями суммарное время должно быть
совместимо с пройденными перегонами. Глобальная: весь рейс и последовательность
рейсов согласованы с теми же якорями. Такие проверки без независимых якорей лишь
оценивают соответствие собственному prior, не истинную stop accuracy.

### 10.3 Масса событий — строгий инвариант

Для каждого route/date/hour **исходной оплаты**:

```text
N_success_source = N_assigned + N_ambiguous + N_unassigned + N_out_of_scope
```

Категории взаимоисключающие, сумма строго целочисленная. Out_of_scope тоже сохраняется
в ledger исходной массы, если событие лежит в конкурсном периоде, но его маршрут
не имеет пригодного pattern. Отдельно учитывать исключённые хвосты ноября и отказы.

Для soft assignments: сумма весов возможных visits + unresolved_weight=1 для каждого
события; сумма expected counts воспроизводит исходную массу с заранее заданной
численной погрешностью. Не округлять каждый soft-weight независимо и не смешивать
soft counts с hard counts. Нужны отдельные таблицы/единицы статуса. Неопределённая масса хранится в отдельном
route/hour bucket со stop_id=null, а не распределяется по известным остановкам.
Soft-кандидат — совместная гипотеза (pattern,direction,journey,sequence); альтернативные
patterns не считаются несколькими реально выполненными посещениями.

Час предполагаемой посадки может отличаться от часа оплаты. Хранить оба; сравнивать
с labels по исходному event hour. Переагрегация по inferred boarding time — новая
цель, не незаметная замена текущей конкурсной разметки.

## 11. Формат результата и объяснение каждого назначения

Предлагаемые экспериментальные артефакты; финальную схему закрепить тестом перед кодом.

| Артефакт | Обязательная информация |
|---|---|
| run_manifest | schema/algorithm/source/graph versions, hashes, event range, timezone, cutoff, compute time, mode, config, seeds, assumptions |
| event_ledger | opaque event_key, event time, success flag, source route, identity outcome, assignment outcome/reason |
| burst_hypotheses | session/burst IDs, interval, counts, devices summary, detector version, split/merge alternatives |
| journey_hypotheses | pattern/direction alternatives, open boundaries, anchor provenance, identity confidence kind |
| visit_candidates | journey+pattern+sequence+stop ID, time interval, emission support, latent/observed distinction |
| event_assignments | event→candidate visits, scores/weights/unknown mass, algorithm version, calibrated=false/true |
| stop_hour_estimates | hard count, expected count, unresolved mass, time basis, inference status, coverage numerator/denominator |
| coverage_ledger | expected visits per candidate, observed/latent/unresolved/external-not-served, residuals, flags |
| evaluation | real-gold, synthetic, stability, plausibility и downstream metrics раздельно |

Reason codes: identity_missing/conflict,clock_anomaly,pattern_missing/unverified,
no_anchor,direction_ambiguous,split_merge_ambiguous,time_incompatible,open_journey,
insufficient_events,source_gap_suspected,search_budget_exceeded,out_of_scope.
Unknown values=null, не stop0/direction0. Флаг calibrated допустим только после
независимой калибровки на отдельной выборке. Даже softmax/top-K weights не являются
калиброванной вероятностью: model posterior условен на принятых priors и гипотезах.
Хранить confidence_kind=score/model_posterior/calibrated_probability явно.

Для объяснения назначения сохранять небольшую локальную трассу: почему этот pattern,
какой anchor, допустимые соседние visits, временной residual, лучшая альтернатива и
почему она отвергнута. Не публиковать raw IDs или строки оплат в review-картинках.

## 12. Этап F — независимая проверка и «золотая» выборка

### F1. Что является gold

Подтверждённые время/остановка/рейс из AVL, фактических журналов или независимо
наблюдённых посещений. Вход reconstruction может оставаться без GPS; GPS используется
только evaluator. Передавать gold в inference запрещено, если эксперимент явно
оценивает восстановление без якорей. Отдельный вариант few-anchor получает только
заранее выделенные якоря, остальные остаются скрытыми для оценки.

Ручная разметка по тем же AFC-всплескам — экспертная гипотеза, не независимый gold.
Фактические посещения сами по себе ещё не дают истинную остановку каждой поздней
оплаты: для event-level gold нужны независимо привязанные события либо наблюдение
посадки. Поэтому gold разделить на visit-level, event-level, count-level; не вычислять
event accuracy по автоматическому nearest-visit и выдавать её за независимую истину.

Начальный запрос данных: два разных маршрута, будний/выходной, пиковые/тихие рейсы,
оба направления, несколько устройств, полные рейсы и обрезанные окна. Проектный
стартовый объём —20–50 independently checked journeys; затем увеличить по фактическим
доверительным интервалам. Этот объём не гарантирует доказательство 95% точности.

Протокол annotations: скрыть предсказания при разметке, два рецензента спорных случаев,
agreement, источник каждого anchor, разрешённая временная погрешность, frozen manifest
и hash. Слепо сравнить predictions после фиксации модели.

### F2. Если gold сейчас недоступен

Можно завершить аудит/симулятор/сопоставление гипотез/оценку устойчивости. Поле
`real_stop_accuracy=unverified`; не назначать `high_confidence` как продуктовый факт.
Сохранить диапазоны допустимых assignments и оценку наблюдаемости. Можно извлечь
burst-only признаки для маршрутной модели, но их полезность не доказывает географию.
Отсутствие gold блокирует promotion, а не всю полезную исследовательскую работу.

## 13. Симулятор, отрицательные контроли и стресс-тесты

Симулятор задаёт истинные visits, движения, boardings и clocks, затем генерирует
только raw-подобные timestamp/device/vehicle поля. Случайность фиксируется. Создать
как минимум две различающиеся генеративные семьи: обучающие priors не должны в
точности совпадать с evaluator simulator. Полученная точность относится к симуляции.

| Испытание | Что должен сделать алгоритм |
|---|---|
| Нулевые посадки на 1/3/5 подряд stops | Пропустить наблюдение без сдвига всех последующих assignments; сохранить ambiguity |
| Первые/последние stops без оплат | Не закреплять первый/последний burst за конечной |
| Один пассажир за несколько stops | Не превращать каждое событие в уверенный stop ID |
| Две близкие остановки, слитые оплаты | Сохранить split-гипотезу/отказ, не forced single stop |
| Одна остановка, два разделённых bursts | Допустить many-to-one, не выдумать дополнительный visit |
| Поздние платежи до следующего stop | Различать boarding time и payment time, шире интервалы |
| Валидаторы с разными offsets | Не объяснять сдвиг исключительно дополнительными stops |
| Пакетные timestamps и массовые повторы | Выставить time-quality flag, не назвать всплеск толпой |
| Несколько вагонов одновременно | Не склеить их в один route-burst |
| Длинная пробка/отстой без разворота | Не менять направление автоматически |
| Короткий разворот/кольцо/повтор stop ID | Сохранять visit sequence, не уникальные названия |
| Исторически неверный pattern | Повысить mismatch/abstention, не подогнать данные любой ценой |
| Отсутствует часть источника | Не подменять missing нулевым спросом |
| Смена route/device в течение дня | Обновить гипотезу identity, не перенести ошибку на весь день |
| Одинаковые интервалы в обоих направлениях | Признать неидентифицируемость без anchor |
| Route5 и пустая выборка | Ноль successful assignments, никаких вымышленных поездок |
| Переход полуночи/границы файлов | Непрерывная сессия, правильный source hour, без двойного счёта |

Дополнительные perturbations на реальных данных: thinning событий, удаление целого
предполагаемого burst, jitter5/15/30 секунд, выпадение устройства, сдвиг предполагаемого
начала, alternate pattern. Это stability tests, не реальная accuracy.

Измерять error recovery после удаления burst: насколько далеко по visits продолжается
сдвиг; устойчивая модель должна вернуться к верной привязке при следующем независимом
якоре либо расширить uncertainty. Метрика особенно важна для цели пользователя
«не съесть остановки».

## 14. Метрики и критерии допуска

### 14.1 Что считать

- Identity coverage: доля исходных successful rows с проверенным vehicle/session.
- Assignment coverage: assigned/all_successful; отдельно conditional coverage внутри
  пригодного каталога и global coverage. Для 10 маршрутов отдельно показать отсутствие
  pattern у пяти, иначе результат четырёх хороших маршрутов скроет половину источника.
- Event exact-stop accuracy только на event-gold; visit precision/recall на visit-gold.
- Ошибка в stop_sequence (median/p90), wrong-direction rate, boundary precision/recall,
  arrival/departure MAE/p90 при соответствующей разметке.
- Lost/extra visits, split/merge counts, maximum consecutive unsupported visits,
  downstream shift length после пропуска. Отличать physical skip от missing observation.
- Risk–coverage curve: ошибка принятых assignments при разных порогах отказа.
- Top-K recall и candidate-set size; огромный набор всех остановок не является успехом.
- Calibration/Brier/log loss только при gold и вероятностных outputs; доверительные
  интервалы bootstrap по рейсам/дням, не по миллионам зависимых событий.
- Stop-hour count WAPE/MAE только против независимо известных counts; global conservation
  проверяется отдельно и не заменяет эту метрику.
- Время/память/events per second, доля budget failures, доля topology/time contradictions.

Срезы обязательны: route,direction,density,peak/offpeak,weekday/weekend,device cohort,
journey completeness,missing-burst length,anchor availability,pattern version quality.
Считать micro по событиям и macro по рейсам/маршрутам. Не выбирать один средний процент.

### 14.2 Гейты

G0 инженерный:100% учёт всех successful rows разрешённого source range,0 задвоений,детерминизм,NaN запрещены,
источник/версии воспроизводимы. Eligibility определяет статус назначения, но не
исключает событие из знаменателя. Любой провал останавливает export.

G1 применимость: недостаточная identity/time/pattern доказательность → только bursts
или relative progress; нет silent fallback на произвольный вагон/stop1.

G2 synthetic: все пограничные случаи и проверка неидентифицируемых примеров пройдены;
не применять требование высокой coverage там, где информации математически недостаточно.

G3 real quality: после появления gold заранее согласовать порог. Предложение пилота:
нижняя 95% граница precision принятых event-назначений≥.95, при этом coverage выше
B2 минимум на 5 процентных пунктов при том же precision; направление отдельно.
Это цель, не доказанное достижение и не обязательство достичь её на текущих данных.
Если event-gold нет, G3 не пройден независимо от visit metrics. Редкие срезы без
достаточной мощности помечать unverified, не объявлять прошедшими по общей оценке.

G4 adoption: при равном качестве выбирать проще/быстрее. Более сложный метод должен
показать paired улучшение по независимым рейсам, устойчивость к пропускам и приемлемый
ресурсный бюджет. Нет выигрыша — оставить baseline, а не усложнять ради названия.

G5 publication: отдельный контракт/UI integration, здесь не выполняется. Даже G3 не
даёт права публиковать оценки как observed data; метод и uncertainty остаются видимыми.

## 15. План сравнительных экспериментов без бесконечного тюнинга

Экспериментальная единица — целый рейс/смена; timestamp split внутри одного рейса
запрещён. Пилотные даты зафиксировать до подбора. Предлагаемая ретроспективная схема:
train январь–июнь, development июль–август, final diagnostic сентябрь–октябрь;
использовать только cohort с пригодной исторической сетью. Эти месяцы уже изучались
в других задачах: не называть весь период полностью слепым. Для нового gold скрыть
часть labels от разработчика до фиксации конфигурации.

1. Сравнить 4–6 конфигураций D0–D3 с одинаковым простым matcher на фиксированном pilot.
   D4 совместно выводит сегментацию и движение: сравнивать его целиком с зафиксированной
   двухэтапной системой, не включать в detector-only абляцию.
2. Заморозить не более 2 детекторов; сравнить B2,DP,HMM,HSMM. Одинаковые anchors,
   время/identity/catalog inputs, одинаковые тренировочные даты и критерий отказа.
3. Не более 24 полных конфигураций в первом цикле. Записать все неудачные варианты,
   бюджет, причины прекращения; не выбрасывать сложные рейсы после просмотра ошибок.
4. Лучший вариант по risk–coverage и constraints freeze → однократная внешняя оценка.
5. Абляции финалистов: без device pooling,без расписания,без density adaptation,
   без skips,без split/merge,без явных durations,без uncertainty refusal,
   без anchors/few anchors. Нереалистичные варианты нужны как отрицательные контроли.
6. Проверить перенос на новые дни, отложенный маршрут, устройства и сценарии низкого
   спроса. Если историческая сеть отсутствует, такой route не считать размеченным holdout.

Offline smoothing может использовать конец завершённого рейса внутри доступной истории.
Online filtering имеет только прошлые события и заданную задержку; это два разных режима
с разными метриками. Для 61-дневного прогноза любой реконструированный feature должен
быть вычислен из событий строго до forecast origin; обрезанный рейс на cutoff остаётся
обрезанным. Хеш features не меняется при модификации future events за cutoff.

Все обучаемые duration priors,burst thresholds,device mappings и calibration fit только
на разрешённой части. Иначе утечка возникает ещё до запуска CatBoost. Новостные факторы
учитывать позже: publication_at≤origin,без применения будущих описаний к прошлому.

## 16. Польза для текущего ML до полноценной геопривязки

Отдельная абляция: число всплесков, квантили их размера, плотность событий,
покрытие устройств/вагонов, доля неопределённых сессий и временных аномалий по
маршруту и часу. Только исторические агрегаты, без raw ID как shortcut-признаков.
Сравнить текущую модель и её вариант с новыми признаками на одинаковых origins.

Stop estimates могут стать weak labels только с сохранённым методом и uncertainty;
не использовать их как gold для оценки следующей модели. Выигрыш маршрутного WAPE
не доказывает правильность stop-ID. Существующий ансамбль до gate не заменять.
Высадки, OD и число людей внутри вагона не входят в первый алгоритм. Onboard load
требует высадок и начальной загрузки; нельзя получить occupancy суммой посадок.

## 17. Производительность и воспроизводимость

Не держать 62 млн строк в RAM. Один проход ZIP → локальные типизированные shards/index
по дате и vehicle/session → внешний sort. Рассмотреть существующий стек; SQLite из
стандартной библиотеки для прототипа либо columnar storage после проверки зависимостей.
Parquet/DuckDB/новая HMM library — кандидаты, не выбранные зависимости. До установки
проверить версию, лицензию, advisories и размер по AGENTS. В рамках плана установок нет.

Декодировать ограниченный набор patterns и временных окон, предварительно считать
cumulative duration bounds, кешировать переходы. На маленьких примерах сравнить DP
с полным перебором, beam search с exact DP и измерить pruning loss. Нормализация
только оставшихся путей не должна скрывать потерянную при pruning неопределённость.

Стартовые бюджеты проектные: 2–4 CPU, 4 GB RAM для offline pilot. Для streaming
latency должна укладываться в выбранную batch-window. Измерить один route-day, затем
неделю и полный период. Записывать hardware, peak RSS, walltime, input bytes,
decoded coverage; не обещать длительность полного запуска до замеров.

Parallel workers ограничивать памятью, временные каталоги делать раздельными.
Checkpoint связан с hash входа/config. Изменение входа требует нового run.
Выходы писать атомарно по завершённым partitions; прерывание не оставляет файл,
который выглядит полностью проверенным. Restart проверяется сравнением с clean run.

| align_dp.py | Exact small / beam large | Сравнение с полным перебором; отказ при симметрии |
| align_hmm.py, align_hsmm.py | Временные states и marginals | Сохранение вероятностной массы, известный маленький posterior |
| confidence.py | Scores отдельно от calibration | Непроверенный score не маркируется calibrated probability |
| aggregate.py | Hard/soft counts и unknown mass | Conservation по исходному часу оплаты |
| evaluate.py, simulate.py | Разделённые виды доказательств | Нет gold → accuracy unverified |
| cli.py | audit/detect/decode/evaluate/export | Старый CLI неизменён, неполный run не экспортируется |

Не создавать все модули заранее: сначала вертикаль audit → bursts → DP → report,
затем добавлять выигравшие альтернативы. Gold хранить отдельно от входов, decoder
не должен получать его путь через общий configuration object.

## 19. Исследовательские основания и переносимость

Источники прочитаны 26.09.2026. Они объясняют методы, но не гарантируют качество на
московских данных. Основной план — наше проектное предложение, требующее проверки.

| Источник | Что берём | Что нельзя переносить |
|---|---|---|
| [Chen & Fan, 2018](https://d-nb.info/1164363093/34), DOI 10.1007/s40534-018-0165-y | Близкий пример AFC без AVL: временные кластеры, route/bus ID, геометрия и оценённое время | Фиксированные 60 секунд/25 км/ч, первый cluster=stop1, заранее заданное первое направление |
| [Newson & Krumm, 2009](https://www.microsoft.com/en-us/research/publication/hidden-markov-map-matching-noise-sparseness/) | Последовательный вывод с топологическими переходами | У авторов есть GPS; их emission model и accuracy не переносятся на логи без координат |
| [Killick et al., PELT](https://arxiv.org/abs/1101.1438) | Штрафуемая сегментация временных режимов | Changepoint не означает географическую остановку; линейная стоимость имеет условия |
| [Johnson & Willsky, 2013](https://www.jmlr.org/beta/papers/v14/johnson13a.html) | Явные длительности HSMM | Не нужен весь непараметрический Bayesian stack; duration model не создаёт якоря |
| [Gordon et al., 2013](https://doi.org/10.3141/2343-03) | Разделение AFC/AVL/linked journeys, внешняя проверка | У нас нет полной сети транзакций и AVL; качество trip chaining не обещаем |

Chen & Fan изучают четыре маршрута, пять дней и 100000 транзакций; 98632 после
очистки — количество, не 98.632% точности. Независимая stop-level accuracy не приведена.
Авторы отмечают увеличение оценки посадок на первой остановке из-за допущения
первого cluster=stop1. Поэтому open start у нас обязателен. Правила удаления повторных
карт из статьи не применять к организаторскому count-rows target.
